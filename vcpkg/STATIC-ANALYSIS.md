# CEF 152: статическая линковка и интеграция vcpkg

## Результат и границы реализации

В репозитории `dobord/cef` сохранён оригинальный upstream-коммит CEF 152.0.6 в ветке `main`. Ветка `vcpkg` содержит закреплённый по версиям overlay-порт для Windows x64 и Linux x64, CMake-пакет, тестовое приложение и GitHub Actions. Реализованный пакет имеет **статическую C++-обёртку и обязательное динамическое ядро**. Он не является полностью статическим CEF и не устраняет зависимость от `libcef.dll` / `libcef.so`.

Главное требование полной статической линковки ядра **не выполнено**. Chromium и `libcef` не компилируются этим портом: ядро загружается из официального minimal-дистрибутива с проверкой SHA-512. Собирается исходный `libcef_dll_wrapper`, содержащий клиентский мост к C API. Эта граница отражена в описании порта, CMake-переменных, именах архивов и машинных отчётах CI; запрос feature `static-engine` завершается явной ошибкой, а не незаметной подменой результата.[1][2]

Контрольный pipeline на коммите `b6c3a6210050a15ccf1d9f65cabb005cbe3ac1b4` успешно собрал порт и запустил Debug- и Release-потребителей на обеих платформах. Проверялись переносимость SDK, отдельный renderer-процесс, IPC, выполнение JavaScript и содержимое полученного off-screen кадра. Это доказательство работоспособности **гибридного пакета**, а не доказательство статической сборки Chromium.[3]

## Зафиксированный релиз

Стабильная версия выбиралась по живому индексу CEF как максимальная версия, одновременно имеющая stable minimal-дистрибутивы `windows64` и `linux64`. Beta-сборки, несовпадающие платформенные версии и старый формат строки версии исключались. Результат зафиксирован 10 сентября 2026 года в 03:08 UTC; последующие сборки не обращаются к плавающему `latest` для выбора версии.[4]

## Сборочный граф: три разных значения «static»

В корневом `BUILD.gn` присутствуют три принципиально разных цели. `source_set("libcef_static")` начинается на строке 517: это набор объектов внутренней реализации с зависимостями Chromium, а не готовый экспортируемый архив. `static_library("libcef_dll_wrapper")` на строке 1292 действительно создаёт статическую клиентскую библиотеку. Итоговое ядро для Windows/Linux объявлено как `shared_library("libcef")` на строке 1939.[6]

Слово `static` в имени внутреннего `source_set` не означает, что CEF распространяет автономный `libcef.a`. Набор объектов включается в другое итоговое звено сборочного графа. Дополнительно в `libcef_sources_common` собирается сгенерированный мост C API, а `libcef_deps_common` включает реализацию, тестовую поддержку и генераторы ресурсов/заголовков. Переключение `BUILD_SHARED_LIBS=OFF` в CMake binary-дистрибутива не меняет эту GN-цель и не пересобирает Chromium.[6]

Аналогично `is_component_build=false` не означает, что конечным продуктом автоматически становится статический SDK: оно не переписывает явное объявление `shared_library("libcef")`. И `/MT` в Windows выбирает способ линковки CRT для компилируемого модуля, а не превращает импортную библиотеку `libcef.lib` в архив кода Chromium.

GN предоставляет `complete_static_lib` для включения зависимостей в статический архив. Это потенциальный строительный блок настоящего static-engine варианта, но не готовое решение упаковки. Отдельно остаются транзитивные системные библиотеки, флаги финального линкера, shared-зависимости, ресурсы, сохранение объектов со статической регистрацией и совместимость инструментария потребителя.[7]

## C++-обёртка и ABI-граница

Клиентская обёртка переводит публичный C++ API в C ABI. Генератор `make_ctocpp_impl.py` создаёт клиентские реализации глобальных функций, которые вызывают C API. В ядре есть собственные реализации одноимённых C++-функций: например, `CefExecuteProcess` и `CefInitialize` в `libcef/browser/context.cc`. Просто связать ядро и обычный wrapper в одном пространстве символов — не то же самое, что соединить готовый клиент с DLL.[8]

Разделение проходит глубже, чем несколько экспортов. Library-side конфигурация задаёт `BUILDING_CEF_SHARED` и `USING_CHROMIUM_INCLUDES`; публичные вспомогательные заголовки при этом могут использовать Chromium-варианты базовых типов. Клиентская сборка использует другой контекст заголовков. Динамическая C ABI-граница позволяет разделять эти детали. После её удаления нужно проверить ODR, встроенные функции, размещение объектов, владение памятью и ABI стандартной библиотеки, а не только устранить первое сообщение о duplicate symbol.[9]

Файл `include/internal/cef_export.h` также ориентирован на текущую модель: MSVC выбирает `dllexport` или `dllimport` по соответствующим определениям. Для static-engine потребуется согласованный режим экспорта во всех участниках сборки. Простое удаление `BUILDING_CEF_SHARED` опасно: этот флаг участвует не только в оформлении экспортов, но и в различении library-side и client-side кода.[9]

У Linux-цели `libcef` уже есть `--allow-multiple-definition`. Это наблюдение об upstream-графе, а не рекомендация скрывать все новые конфликты тем же флагом. Успешная линковка с подавленными конфликтами ещё не доказывает, что выбрана правильная реализация каждой функции.[6]

Практичный первый исследовательский вариант настоящего статического ядра — отдельный **C API-only** потребитель без стандартной C++-обёртки. Он уменьшает число пересекающихся C++-определений и зависимость клиентских заголовков от STL ядра. Это проектное направление, **не реализованная и не проверенная возможность текущего порта**. Поддержка привычного C++ API потребовала бы самостоятельной проработки изоляции и генерации моста.

## Особенности Windows

Проверенный triplet — `x64-windows-static`. Обёртка компилируется как статическая библиотека с CRT, выбранной toolchain; Debug и Release потребители используют согласованные настройки своего wrapper. Для CMake/Ninja сохранены флаги vcpkg, которые исходный CEF CMake-код на Windows очищает. Экспортированы транзитивные системные зависимости, delay-load `libcef.dll` и размер стека 8 MiB.[2][10]

Файл `libcef.lib` в официальном Windows-дистрибутиве является **импортной библиотекой DLL**, несмотря на расширение `.lib`. В пакете он размещён рядом с runtime, а не выдан за статический движок. Реальная статическая библиотека — `libcef_dll_wrapper.lib`. Debug wrapper и Release engine могут сосуществовать через существующую C ABI-границу; это не означает, что такой же набор CRT можно без изменений объединить в один полностью статический executable.

Отдельного решения требует bootstrap/sandbox. Текущий порт не поставляет Windows bootstrap/sandbox-интеграцию. В smoke-приложении явно включён `no_sandbox` для фиксированного локального тестового документа. Успешный запуск такого теста нельзя представлять как доказательство работоспособности sandbox или как безопасную конфигурацию для произвольного веб-контента.[1][11]

Инструментарий сборки wrapper и инструментарий сборки ядра также различаются. Проверенный binary-SDK потребляется Visual Studio 2022. Документ Chromium именно для тега `152.0.7977.83` описывает собственные требования к clang-cl, Visual Studio и Windows SDK. Нельзя автоматически переносить успешную сборку wrapper на полный source-build Chromium.[12]

## Особенности Linux

Проверенный triplet — `x64-linux`, runner — Ubuntu 24.04. Потребитель собирается GCC, использует C++20 и линкуется со статическим wrapper; `libcef.so` остаётся обязательной динамической зависимостью. Экспорт CMake включает Threads, X11 и `dl`. Для размещённого рядом runtime используется `$ORIGIN`; тест проверяет разрешение зависимостей уже после переноса приложения.[2][3]

Архив ядра Chromium, в отличие от wrapper, привязан к его собственному toolchain и STL. Официальная инструкция Linux указывает Clang и libc++ как поддерживаемый инструментарий, минимум 8 GiB RAM и 100 GB свободного диска; объём памяти выше 16 GiB рекомендуется. Эти требования объясняют необходимость отдельной инфраструктуры для source-build, но сами по себе не доказывают невозможность статической модификации CEF.[13]

«Статическое ядро CEF» нужно отличать и от полностью статического ELF без системных shared libraries. Отказ от `libcef.so` ещё не означает статическую линковку glibc, графического стека и всех вспомогательных библиотек. Для настоящего static-engine пакета потребуется явный контракт допустимых внешних зависимостей и соответствующая проверка `DT_NEEDED`/загруженных модулей.

## Ресурсы и subprocess

Статическая линковка сама по себе не устраняет `icudtl.dat`, V8 snapshot, resource packs и локализации. Перечни runtime-файлов в CEF CMake включают также платформенные графические компоненты. Реализованный порт сохраняет runtime/resources в `tools/cef` и предоставляет `cef_deploy_runtime(target)` для копирования полного комплекта к executable.[10]

Наличие `.a` или `.lib` не проверяет маршрутизацию browser/renderer-процессов. Тестовое приложение вызывает `CefExecuteProcess` в общей точке входа и лишь в основном процессе выполняет `CefInitialize`. Отдельный renderer сообщает свой PID через CEF process message. Проверка требует, чтобы этот PID отличался от PID browser-процесса: режим `--single-process` не используется.[1]

На Linux точка входа дополнительно помечена `NO_STACK_PROTECTOR`, как в upstream-примере, учитывая поведение Chromium после fork. Нельзя переносить этот частный атрибут в рекомендацию отключать защиту стека всего приложения.[14]

## Что проверяет CI

Основная матрица запускается на изменениях `vcpkg`, pull request в эту ветку и событии `release.published`. На каждой платформе поднимается отдельный закреплённый checkout vcpkg, собираются Debug/Release wrapper, выполняется обычная post-build validation vcpkg и экспортируется SDK.[2]

Потребитель конфигурируется из перенесённого SDK. Исходная установка vcpkg переименовывается, приложение копируется ещё раз, а SDK на время запуска скрывается. Это проверяет отсутствие случайной зависимости от исходного расположения. На Linux дополнительно записываются `ldd` и динамическая секция ELF; в доказательствах сохраняются журналы и JSON каждого запуска.

Smoke-тест создаёт локальный `data:` документ, вычисляет `6 * 7` в JavaScript и проверяет заголовок `CEF_SMOKE_42`. Off-screen обработчик проверяет ожидаемый BGRA-пиксель фона в кадре 320×240. Проверяется получение IPC из другого PID и корректное завершение через закрытие браузера, message loop и `CefShutdown`.[1]

Первый запуск CI обнаружил ошибку самого теста: `CefURIEncode(..., true)` кодировал пробел как `+`, что не подходит для пробела внутри HTML в `data:` URL. Это мешало применению ожидаемого CSS. Исправление использует percent-encoding без замены пробела на `+`; добавлены журналы стадий, фиксированные scale factor и color profile. После исправления обе платформы прошли проверки без ослабления требований к JavaScript, IPC или пикселю.[3][15]

Дополнительно проверялись 24 upstream Python-теста выбранных генераторов на Linux. 23 прошли; один golden-тест `make_config_header_test` не прошёл: фактический результат содержал `CEF_X11`, а общий golden-файл — нет. Эта проверка не является полным тестовым набором CEF; исходный golden-тест не менялся. Полная попытка discovery была остановлена по таймауту и не засчитывается как успешный прогон.[16]

За пределами проверки остаются sandbox, GPU-ускорение, WebRTC, аудио/видео, внешняя сеть/TLS, accessibility, crash reporting, поддержка других версий Windows/Linux и полная матрица Chromium/CEF. Наличие этих ограничений не отменяет проверенный запуск, но ограничивает вывод о готовности пакета.

## Архивы и релизы

Имена SDK заканчиваются на `static-wrapper-shared-runtime`, чтобы тип линковки был виден до скачивания. Внутри сохраняются lock-файл и build receipt; рядом создаётся SHA-256 архива. Receipt явно содержит `engine_linkage: shared`, `wrapper_linkage: static`, `full_static_engine_verified: false` и `sandbox_verified: false`.[2]

Release-job зависит от успешного завершения обеих архитектурных jobs. Права записи содержимого выдаются только job публикации; обычные сборки имеют read-only доступ. Загружаются ровно два SDK и две контрольные суммы. Существующие release assets не перезаписываются. Бинарные входы проверяются SHA-512, а Actions закреплены полными commit SHA.[2]

Тег релиза должен указывать на коммит ветки `vcpkg`, содержащий workflow. Ветка `main` намеренно остаётся оригиналом и не содержит integration workflow. Создание релиза по обычному `main` нельзя считать эквивалентом релиза интеграции. Event `published` описан в документации GitHub; фактическая проверка build/smoke в основном run выполнялась по событию `push`, не по `release.published`.[17]

Для проверки доставки архивов выполнена отдельная техническая проверка: готовые ZIP загружаются на новые Windows/Linux runners, извлекаются, используются для сборки Debug/Release потребителей и запускаются со скрытым SDK. Только после успеха архивы и отчёты прикрепляются к **неопубликованному** техническому draft release. Эта проверка успешно завершена в run `34434605354`; загружены два SDK, два SHA-256 файла и два JSON-отчёта. Результаты и ссылки приведены в `STATUS.md`. Черновик не опубликован; эту проверку нельзя смешивать с событием `release.published` или с проверкой статического ядра.[18]

## Что требуется для настоящего static-engine варианта

Нужна новая, отдельная цепочка сборки ядра из закреплённых CEF/Chromium sources и согласованного toolchain. Она должна создать целостный архив реализации и зависимостей, согласовать exports, удалить зависимость потребителя от импортной библиотеки `libcef`, сохранить необходимые ресурсы/регистрации и экспортировать полные требования финальной линковки. Правки должны проверяться реальным GN generation, компиляцией и линковкой, а не только текстовой заменой типа target.

После получения архива необходим потребитель, который работает **без установленного или развёрнутого `libcef.dll`/`libcef.so`**, включая renderer/utility процессы. Статический C++ API требует дополнительной проверки символов и ABI; C API-only вариант мог бы служить первым этапом. Debug/Release, CRT, системные shared-зависимости и sandbox должны иметь явную спецификацию и тесты, а не неявные предположения.

Критерий завершения — обе платформы из чистой среды собирают именно ядро, экспортируют переносимый vcpkg-пакет, линкуют независимое приложение и запускают его с проверкой отсутствия динамического `libcef` в импортах и загруженных модулях. Ни один из этих результатов для static-engine здесь не получен. Поэтому текущая поставка — проверенная интеграционная база и исследование, **не завершённая реализация первоначального требования полной статической сборки**.
